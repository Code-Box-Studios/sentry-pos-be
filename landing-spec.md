# Sentry — Landing Spec

**Surface:** apex route of the portal app (`sentry-pos-fe`) · **Ships:** milestone 3 · **Updated:** 2026-08-19

One public page. Its job is credibility after a pitch, a Sign-in door for existing BOs, and a public home for the ToS and privacy policy. It is not a funnel — there is no self-signup, so there are no forms beyond a request-access mailto. Full design language per `design-spec.md` (Figtree self-hosted, dark-teal bands, green pills), statically rendered, effectively zero client-side JavaScript.

## 1. Page Structure (top to bottom)

1. **Nav** — sticky white bar: Sentry wordmark left; right, a single green pill **Sign in** (links to `app.` login). Nothing else; a one-page site needs no menu.
2. **Hero** (`hero-band-dark`) — H1 is the tagline: *"Your business, always in sight."* One-sentence sub: what Sentry is, for whom (multi-branch POS with profit analytics for Philippine businesses). CTAs: green pill **Sign in**, outlined-on-dark **Request access** (mailto to the support address). Below the CTAs, a product-shot card in the mockup-card slot — the portal dashboard screenshot where MongoDB would show a terminal.
3. **Feature trio** — three `card-base` cards, 3-up desktop collapsing per the design spec: **The counter** (fast grid-and-barcode sales, receipts, shifts and Z-reports) · **The numbers** (profit, not just sales — daily email, calendar heatmap, leaks) · **The record** (every action by every user, logged completely). Icons from the design system's category-tag palette, used sparingly.
4. **Detail band** — one two-column section: a second screenshot beside four short bullets (multi-branch with transfers, inventory with expiry tracking, SC/PWD-compliant discounts, remote terminal control).
5. **CTA banner** (`cta-banner-dark`) — one line and the Request-access pill.
6. **Footer** (dark teal) — support email, **Terms of Service**, **Privacy Policy**, © Code Box Studios.

## 2. Copy Rules

Sentence case, verb-first, contractions fine, zero hype vocabulary ("seamless", "empower", "unlock" are banned). Prices and pesos may appear in screenshots but the page makes no pricing claims. **The honesty rule:** the page describes only shipped features — no offline claim until milestone 4 delivers it, no staff-roles claim until that phase ships. Copy updates ride feature releases.

## 3. Meta, SEO & Analytics

- Title: "Sentry — POS and business monitoring for Philippine businesses". The meta description leans into the PH-POS framing to differentiate from sentry.io in search results.
- OG image: the dashboard product shot. Sitemap and robots generated by Next.
- Analytics: Vercel Analytics only (cookieless) — which also means no cookie banner. No trackers.

## 4. Content Model

Every editable string on the page lives in **one typed object** — nothing hardcoded in components:

```ts
LandingContent {
  meta:     { title, description }
  hero:     { headline, sub, primaryCta, secondaryCta, screenshot }
  features: { icon, title, body }[3]
  detail:   { screenshot, bullets[4] }
  banner:   { line, cta }
  footer:   { supportEmail, links }
}
```

This shape is the contract: components render it, and it works identically as a repo file or a CMS collection.

## 5. Content Editing — Payload CMS (day one)

**Decision:** Payload 3, mounted inside this same Next app, from launch. The `LandingContent` object becomes a Payload **global** (singleton) one-to-one — one page, one record.

Integration guardrails:

- **Route:** admin UI at **`/cms`** — never `/admin`, which belongs to the Sentry platform panel. Excluded from robots; Payload's built-in login throttling applies.
- **Database:** a dedicated **`cms` schema** in the same Supabase project. Payload's migrations run independently there; Prisma and the POS schema never touch it.
- **Auth:** standalone — a single CMS user with its own credentials, deliberately separate from the platform-admin identity. A compromised CMS login reaches marketing copy, nothing else.
- **Media:** Payload's S3 storage adapter pointed at a **public** Supabase Storage bucket (landing images are public content); the private tenant bucket is untouched.
- **Publishing:** ISR with an on-demand revalidation hook — Payload's `afterChange` pings the revalidate endpoint, so edits go live in seconds while visitors keep getting a static page.

If the site grows (blog, multi-page), new content types are added as ordinary Payload collections in the same `cms` schema — the infrastructure is already paid for.

## 6. Engineering Notes

Static generation with on-demand ISR revalidation from Payload, `next/image` for the screenshots, Figtree via `next/font`, Tailwind mapped from `design-spec.md` tokens. Lighthouse budget: the page is one route with two images — anything below ~95 performance is a regression, not a tradeoff.
